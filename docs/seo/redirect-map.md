## Защищённые области

Это минимальный перечень для сверки с администратором, а не полная карта хостинга. Никаких автоматических удалений вне отдельного утверждённого списка.

- `app/`, включая серверные `app/signature.php` и `app/get_invoice.php`: зависимости API вне репозитория; не читать содержимое и не удалять.
- `php/api/`, `php/mailer/`, `php/deploy/` и серверные `config.php`: сохранить API, отправку заявок, публикацию и конфигурацию. Секреты не включать в отчёт/логи.
- `.env`, `.htaccess`, `.user.ini` и прочая серверная конфигурация, сертификаты и служебные файлы хостинга: сохранять; точечное изменение правил возможно только после отдельного согласования. Корневого `.htaccess` в репозитории нет.
- Клиентские документы, загрузки, базы/данные, логи, резервные копии и временные каталоги: фактические пути выяснить у администратора, не запрашивать содержимое; не считать остатками сборки.
- `files/`, `img/`, `fonts/`, `css/`, `js/`, `vendor/`, favicon, все актуальные HTML и служебные `client-doc.html`, `controls.html`, `order-ok.html`, `index.html`: не затрагивать SEO-очисткой.
- `robots.txt` сейчас существует только на сервере; сохранить до воспроизводимого переноса в SEO-03. `sitemap.xml` сохранить.
- Подтверждённые серверным списком `app/`, `error/`, `/order-print.html`, `/letsencrypt.html` и файл верификации `/yandex_9dbf96c41ebeed6c.html` исключить из очистки. Полные 14 защищённых HTML перечислены в реестре; содержимое не запрашивалось.

## Выводы по механизму публикации

`gulp/deploy-z.js` получает серверный список, проходит **весь** `public/` и удаляет из рабочей копии списка все найденные локальные пути, включая неизменённые. Остаток, выводимый перед отправкой, — кандидаты «сервер минус полная сборка», но не список на удаление: в нём могут быть конфиги и серверные данные.

Архив содержит **только изменённые файлы**. `src/php/deploy/deploy.php` вычисляет `missing_files` как разность серверного списка и содержимого этого инкрементального архива; поэтому туда попадают и актуальные неизменённые файлы. PHP копирует новые/изменённые файлы, но не очищает document root; `recursiveDelete` удаляет только временный каталог распаковки. JS удаляет `missing_files` из выводимого ответа.

**Нельзя удалять по `missing_files`, составу архива или одному факту отсутствия в репозитории.** В коде публикации изменён только набор входных путей: явно добавлен `public/.htaccess`, который скрытый glob иначе не подхватывает. Механизм сравнения, инкрементального архива и отсутствие удаления сохранены.

### Проект контроля остатков для следующей задачи

1. После чистой успешной сборки формировать полный манифест относительных путей артефактов (при необходимости — хешей), независимо от списка изменённых файлов. Не включать секреты и абсолютные пути.
2. Сравнивать полный манифест с отдельно согласованным серверным списком. Для SEO достаточно отчёта по HTML; серверные/неизвестные области защищены по умолчанию.
3. Хранить предыдущий манифест управляемых артефактов: даже ранее управляемый файл после исчезновения из сборки только кандидат на ручное рассмотрение.
4. Выводить отдельный read-only отчёт: управляемые текущие / кандидаты на снятие / защищённые / неизвестные. Новый неизвестный HTML требует разбора, а не автоматического удаления.
5. Применять только версионируемую явно утверждённую карту точных URL. Синхронизация с удалением не предлагается. Последующие публикации должны сохранять согласованные 301/410 и проверять их HTTP-тестами.

## Проверка конфигурации перед реализацией

2026-10-16 повторные публичные GET `/`, `/pricing.html`, `/pricing20220201.html` и `/truck-service.html` показали заголовок `Server: nginx/1.31.3`. Корень по-прежнему отвечает 301 на `https://bergvl.ru/home.html`, остальные три URL — 200. Это подтверждает внешний nginx, но не устанавливает, есть ли за ним Apache и обрабатываются ли статические HTML до `.htaccess`.

В репозитории `src/php/.htaccess` содержит `Require all denied`, а `src/php/mailer/.htaccess` — точечные разрешения обработчиков. Эти файлы не описывают корневую маршрутизацию; менять их ради SEO нельзя. Наличие корневого `.htaccess` в серверном списке не доказывает, что nginx передаёт ему запросы HTML.

Действующий корневой `.htaccess` предоставлен владельцем 2026-10-16. На его основе подготовлен `src/.htaccess`: перед существующими правилами добавлены пять точных 301 с `QSD` и четыре точных 410 с `G`. Остальная конфигурация сохранена. `QSD` требует Apache 2.4+ ([документация флагов](https://httpd.apache.org/docs/2.4/rewrite/flags.html)).

`gulp/copy.js` копирует корневой файл в `public/.htaccess`, `gulp/deploy-z.js` явно включает его в набор публикации. При следующем деплое этот файл **может заменить корневую серверную конфигурацию**: перед выпуском обязательно сверить её текущую версию с предоставленной, сохранить резервную копию и проверить порядок правил.

Локально успешно выполнены `npm run build`, `npm test` (21 тест, в том числе 4 новых), `npm run lint`. Тесты проверяют структуру правил, сохранение прежних директив, копирование файла и включение в glob публикации. Это не исполнение правил Apache. `httpd`/`apachectl` локально не обнаружены; серверная проверка синтаксиса и HTTP-поведения не выполнена.

**Блокер проверки перед выпуском:** требуется уточнение у хостинга, обслуживает ли nginx существующие `.html` напрямую. Если да, требуется соответствующий фрагмент server/location nginx либо способ задания редиректов в панели хостинга. Полную конфигурацию, ключи и пароли предоставлять не нужно. Deploy API не предоставляет содержимое файлов; добавлять ради этого серверный файловый доступ не предлагается.

После получения конфигурации подготовить точечное дополнение, не замену неизвестных правил, проверить синтаксис доступным серверным средством и согласовать отдельный выпуск с резервированием. Правила созданы локально, но не опубликованы; конфигурация nginx/Apache и фактическое исполнение `.htaccess` ещё не подтверждены.

## Порядок отдельного выпуска

### До изменения

1. Серверный список HTML получен и сверен; перед выпуском обновить его. 410 для schedule/gradient согласованы владельцем 2026-10-16, статус услуг также подтверждён. Выяснить веб-сервер, document root, алиасы, приоритет существующих правил и поведение query string. Правила не должны зависеть от query string и не должны переносить ненужные параметры архивных прайсов на целевой URL.
2. Получить явное разрешение на конкретный выпуск. Публикация/удаление не следуют автоматически из начала SEO-задач.
3. Администратор делает вне публичного document root резервную копию затрагиваемых HTML и конфигурации с правами/временем изменения. Зафиксировать путь и ответственного в закрытом журнале, проверить читаемость/восстановление без публикации секретов.
4. Сохранить исходные HTTP-коды/Location и проверить целевой `/pricing.html` (200). Проверить точные правила на тестовом окружении с аналогичной маршрутизацией: архивный URL должен обрабатываться и при наличии старого физического файла.

### Применение

1. Внести только согласованные правила точных путей подходящим для сервера способом. Локальный `.htaccess` подготовлен на основе предоставленного владельцем; перед применением сверить серверную конфигурацию и подтвердить обработку HTML через Apache.
2. Сначала проверить маршрутизацию. Физически удалять файлы для работы редиректа не обязательно; если снятие файлов требуется, это отдельный явный список и перемещение в закрытую резервную копию, не массовая очистка.
3. Не менять `/` → `/home.html`, существующие PHP, клиентские документы и актуальные файлы. Не блокировать старые URL в robots.txt: робот должен получать согласованный HTTP-статус.

- Повторить read-only сверку HTML и зафиксировать дату, итоговые HTTP-коды и исполнителя. 301 кешируется: проверить CDN/прокси и свежий запрос, не полагаться только на браузерный кеш.

### Откат

При неверном статусе, цикле, ошибке цели или регрессии актуальных страниц: остановить выпуск; вернуть только изменённые правила из резервной копии, восстановить только затронутые перемещённые HTML, при необходимости сбросить согласованные кеши. Повторить GET исходных и контрольных URL; сравнить с исходным реестром. Учитывать, что ранее закешированный браузером 301 может сохраняться после серверного отката. Массовое восстановление document root поверх серверных данных не использовать.
