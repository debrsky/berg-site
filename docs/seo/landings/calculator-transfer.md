# Калькулятор → заявка: перенос веса и объёма

## Разрешение и приоритет

После просмотра калькулятора владелец спросил о переносе веса/объёма и подтвердил реализацию предложенного поведения: передавать только введённые пользователем параметры, не выдавать оценочные значения за введённые, не перезаписывать сохранённую заявку молча.

Это согласованное расширение прежнего контракта «только города» **для перехода калькулятор → order.html**. Ссылки лендингов по-прежнему передают только города. Сам калькулятор не принимает вес/объём из query. Новые поля формы, PHP/JSON-контракт, алгоритм цены, ставки и состав целей не менялись.

## URL и проверка значений

Пример: `order.html?origin=vvo&destination=khb&weight=500.5&volume=1.125`.

- origin/destination проходят прежнюю проверку известной направленной тарифной пары, без повторов параметров.
- weight (кг) и volume (м³) необязательны. Передаются только фактические значения соответствующих input калькулятора; оценки из readInput/processCalc не используются.
- Если введён только вес — передаётся только weight; только объём — только volume. Отсутствующий параметр не вычисляется и не подставляется в заявку.
- Положительные десятичные числа с точкой/запятой, без знаков, пробелов, суффиксов и экспоненты. Точность как у масок калькулятора: 1 знак веса, 3 знака объёма; без округления. Строка максимум 32 символа, конечное значение не выше Number.MAX_SAFE_INTEGER. Это защитные ограничения переноса, не новые бизнес-ограничения приёма груза; ручная заявка остаётся доступной.
- В query значения нормализуются с точкой и без лишних нулей; в полях заявки — с запятой. Восстановленные численно совпадающие значения сохраняют свой формат, включая дополнительные десятичные нули.
- Повторный, пустой или некорректный weight/volume делает весь входящий грузовой набор недопустимым: оба параметра груза игнорируются. Валидная пара городов при этом может применяться отдельно.
- Нет валидной пары городов — нет переноса груза. Для неподдерживаемой пары ссылка калькулятора ведёт на обычную order.html без query.
- Остальные поля, в том числе количество мест, наименование, специальные условия, объявленная стоимость, контакты и согласие, из URL не принимаются.

## Порядок и защита сохранённых данных

1. Сначала штатное восстановление заявки на DOMContentLoaded.
2. Затем прежнее решение о городах: пустая пара применяется, совпадающая сохраняется, конфликтующая/частичная сохраняется с уведомлением.
3. При конфликте городов вес/объём тоже не применяются; уведомление явно сообщает об этом.
4. Для принятого/совпадающего маршрута сравниваются только переданные параметры груза. Если хотя бы один из соответствующих заполненных input отличается, весь входящий грузовой набор не применяется; показывается уведомление. Не оставляется смесь из нового веса и конфликтующего старого объёма или наоборот.
5. Если конфликта нет, заполняются только пустые поля, для которых передано значение. Совпадающие заполненные поля и поля, отсутствующие в URL, не изменяются.
6. После применения — обычный change, штатная структура/валидация и сохранение. Кнопки очистки/последней заявки, ручной ввод и back не запускают повторную подстановку query на каждом действии. При reload сохранённые значения проходят ту же проверку конфликта.

## Реализация

- `src/js/common/calculator-transfer.js`: общий валидатор величин, builder ссылки по исходным input, парсер грузового набора и защита существующих полей.
- `src/js/calculator.js`: обновляет href CTA из реальных значений input, а не оценённых параметров расчёта.
- `src/js/route.js`: после восстановления вызывает маршрутное/грузовое предзаполнение только для заявки; калькулятор по-прежнему получает из query только города.
- `src/pages/calculator.pug`: пояснение о переносе и сохранённых данных.
- `tests/calculator-transfer.test.js`, `tests/route-persistence.test.js`, `tests/calculator-ui.test.js`: проверки контракта и регрессии.

## Безопасность и аналитика

Вес/объём присутствуют в URL перехода, но не добавляются в самописные параметры целей, route-source, UTM/yclid или отдельные поля письма. Canonical order.html остаётся чистым; query-варианты в sitemap не добавляются. Согласие автоматически не устанавливается; ничего не отправляется без пользователя. PHP и генератор JSON не изменены: значения попадают в существующие поля груза обычной формы.

## Проверки

- build, **51/51 тест**, lint, diff-check — успешно.
- Unit: десятичные форматы/границы точности, ноль/отрицательные/экспонента/Infinity/длинные/XSS-строки, повторные/неполные параметры, игнорирование прочих полей, route conflict, cargo conflict, совпадение/частичное заполнение, сохранение формата и согласия.
- Persistence: восстановление перед применением, запись нового веса/объёма, конфликт после reload, очистка и последняя сохранённая заявка, недоступное хранилище.
- Chromium в отдельном тестовом контексте: 500,5 кг / 1,125 м³ → существующие поля 500,5 / 1,125; reload сохраняет их. Изменённые 100 кг не затираются, показывается уведомление. Очистка оставляет пустые поля без повторного применения.
- Только 500 кг → заявка без объёма; только 0,125 м³ → заявка без веса. Возврат в калькулятор сохраняет исходный ввод и правильный href.
- Конфликт маршрута сохраняет старые города и параметры груза; некорректный volume игнорирует оба параметра груза; запрет sessionStorage не мешает предзаполнению; accept остаётся выключенным. Ошибок в консоли нет.
- Реальные заявки не отправлялись. Приём целей Метрикой, mailer и production не проверялись; публикация не выполнялась и не разрешена.
