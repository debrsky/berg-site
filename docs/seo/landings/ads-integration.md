# SEO-04: дополнение для контекстной рекламы

Дата: **2026-10-16**. Текущий статус: **детали подтверждены владельцем в продолжении сессии**: маршрутные телефоны/CTA, защита восстановленных городов, цели и атрибуция 30 минут, переход калькулятор → заявка с текущими городами. Отдельным запросом разрешена реализация Владивосток → Хабаровск и необходимой общей интеграции; [локальный результат](implementation-vvo-khb.md). Настройки кабинетов и публикация не выполнялись. Ниже — согласованный контракт; исторические указания «предложение» не отменяют это подтверждение.

Это дополнение имеет приоритет над первоначальным ограничением «заявка без предзаполнения» в черновиках SEO-04. Не означает утверждения всех трёх прототипов или разрешения на вёрстку/выпуск без согласования.

**Позднейшее разрешение владельца:** перенос введённых веса/объёма из калькулятора в заявку реализован по [отдельному контракту](calculator-transfer.md). Он имеет приоритет над прежним запретом числовых параметров в URL заявки; остальные поля/согласие по-прежнему не принимаются, калькулятор из URL получает только города.

## Что согласовано по направлению

- Одни и те же три лендинга предназначены для SEO и контекстной рекламы; отдельные рекламные копии/дубли не нужны.
- Объявление, маршрут, тарифы, сроки и телефон посадочной страницы должны соответствовать друг другу.
- Учесть UTM/yclid, атрибуцию и успешные заявки до рекламного запуска.
- Предусмотреть предзаполнение маршрута **и в калькуляторе, и в существующей заявке** как отдельную общую интеграцию.
- Не считать клики по CTA и телефону реальными заявками/звонками. Коллтрекинг — опция, не согласованная закупка или интеграция.

## 1. Первый экран и соответствие объявлению

Для каждого маршрута видимы H1, обычный срок, гарантированный максимум/пояснение, CTA расчёта/заявки и контакт отправления либо заметная ссылка на него. Не делать обещание «гарантированно за сутки» из обычных суток и не выдавать документный минимум за цену любой перевозки.

Контакт первого экрана выбирать **по отправлению маршрута**, а не по DaData, localStorage выбранного города шапки или местоположению посетителя. Общая шапка может сохранить текущую механику, но не должна заменять маршрутный контакт в контенте.

Предложенная поправка прототипов: на vvo→khb/khb→vvo добавить компактный tel-контакт приёмки в hero; на vvo→blg рядом с CTA согласования явно показать контакт отправки. Окончательное размещение согласовать вместе с прототипами.

## 2. Рекламные параметры и canonical

Тестовые URL (условные метки, не настройка реальной кампании):

```text
/vladivostok-khabarovsk.html?utm_source=yandex&utm_medium=cpc&utm_campaign=route_test&yclid=test_click
/khabarovsk-vladivostok.html?utm_source=yandex&utm_medium=cpc&utm_campaign=route_test&yclid=test_click
/vladivostok-blagoveshchensk.html?utm_source=yandex&utm_medium=cpc&utm_campaign=route_test&yclid=test_click
```

- Эти URL должны открывать тот же контент со статусом 200. Не удалять query до того, как Метрика сможет обработать рекламный визит; при неизбежном редиректе на целевой рекламный URL сохранить параметры.
- Canonical всегда чистый self-URL без UTM/yclid. В sitemap только чистые URL, не создавать индексируемые копии под кампании.
- Внутренние ссылки **не размечать UTM**: это не способ сохранять источник. Проверять обычную атрибуцию визита Метрикой при переходе лендинг → калькулятор → заявка в пределах того же сайта.
- Не копировать полный query/referrer в самописные параметры целей, письма, логи или sessionStorage. В первоначальный объём не включать хранение UTM/yclid в форме, PHP и CRM. Для CRM/офлайн-конверсий потребуется отдельное согласование схемы данных и приватности.
- Не менять действующий `QSD` у старых архивных прайсов: реклама должна вести на конечные актуальные лендинги, не на старые URL. Не отменять согласованные 301/410 из SEO-01.
- Динамическую подмену текста по `{keyword}`/произвольным query не добавлять. Условия и цены берутся из утверждённых источников.

## 3. Предлагаемый контракт маршрутного предзаполнения

Параметры одинаковы для калькулятора и заявки:

```text
calculator.html?origin=vvo&destination=khb
order.html?origin=vvo&destination=khb
```

Другие две пары: `khb/vvo`, `vvo/blg`. В калькуляторе поля — `origin`/`destination`; в форме заявки существующие select **`loading-place`/`unloading-place`**, значения — коды из tariffs. Новые поля, изменение JSON/серверного обработчика или фоновая отправка не нужны.

### Предлагаемые правила

1. Один общий парсер/валидатор: ровно по одному origin и destination, оба кода известны, направленная пара поддерживается тарифами, origin ≠ destination. Неполная/повторная/неизвестная/неподдерживаемая пара — игнорировать оба, не оставлять смесь из URL и старой формы. Не разрешать произвольное значение `other` через URL.
2. Из URL в калькулятор брать **только города**. В заявке, по позднейшему разрешению владельца, допускаются также проверенные weight/volume из калькулятора с защитой сохранённых данных ([контракт](calculator-transfer.md)). Не подставлять ФИО, телефоны, адреса склада, даты/время, оплату, чекбоксы и согласие. Никакой автоотправки заявки. Флажок `accept` не устанавливать автоматически.
3. Для новой пустой формы — применить оба города и штатное обновление структуры/required/валидации. Ради предзаполнения не менять тарифный расчёт или формат mailer JSON.
4. Сохранённую/восстановленную форму не перезаписывать молча. Если пара уже совпадает — оставить. Если заполнены другие города или только один — сохранить данные и показать короткое уведомление о конфликте с предложением проверить/поменять города вручную. Это **предлагаемое** правило защиты введённых данных, требуется согласование владельца.
5. Не переустанавливать города на каждом change/input/pageshow; ручной выбор и восстановление из истории имеют приоритет после начальной загрузки. Кнопки «Очистить» и «Заполнить по последней заявке» должны сохранить понятное поведение, не возвращать URL-пару неожиданно после каждого действия.
6. Работать без хранилища, где это возможно; при отсутствии/ошибке сохранённых данных — не падать, оставить ручной ввод. Не выводить содержимое сохранённых заявок в логи/тестовые отчёты.
7. Без JS города не предзаполняются; на лендинге остаются тарифы, условия и маршрутный телефон. Не обещать полностью работающую форму/калькулятор без JS.
8. Canonical `order.html`/`calculator.html` остаётся без параметров, параметризованные URL не добавляются в sitemap.

### Особенность текущего кода

`src/js/order.js` вызывает `enablePersistance(form)` из **`src/js/form/persistance.js`** (имя файла именно такое). Восстановление выполняется на DOMContentLoaded через `formDeserialize`, которая сначала вызывает `cleanForm` и change. Предзаполнение нельзя вставлять перед восстановлением: восстановление может его стереть. Нужно спроектировать явный порядок «восстановление → решение о конфликте → применение пары → штатное обновление структуры», проверить запись в sessionStorage и обратную навигацию.

Не обходить конфликт отключением сохранения формы. До реализации прочитать `src/js/form/utils.js`, `src/js/order/form-structure.js`, `required.js`, `custom-validity.js`, `make-json.js` и тесты отправки.

### Текст CTA после интеграции

На лендинге: «Маршрут будет предложен в заявке. Проверьте города отправления и получения перед отправкой». При восстановленной конфликтующей форме — уведомление в форме, а не обещание безусловного переноса. До готовой интеграции допустима только старая обычная ссылка на order.html с честной инструкцией ручного выбора.

## 4. Конверсии и атрибуция

- Подключить/проверить существующий счётчик Метрики в рекламной кампании и выбрать подтверждённую успешную отправку как основную конверсию. Настройки кабинетов выполняются только с доступом/разрешением владельца, не считаются сделанными по наличию кода.
- Сохранить существующую цель **`order successfully sent`**. Дополнительные цели `route_*` и разрешённые параметры описаны в README; названия и модель атрибуции пока предложены, не утверждены как настройки кабинета.
- Успех — только `data.result === 'success'` в действующем потоке отправки. Не считать успехом клик Submit, HTTP 200 без success, загрузку order-ok, клик калькулятора или tel-ссылки. Сбой ym не должен мешать заявке/переходу.
- Собственная маршрутная атрибуция: только whitelist пары/slug/позиции CTA, без рекламных меток и клиентских полей; sessionStorage с TTL 30 минут — предложение. Контекст источника не является фактическим маршрутом после ручного редактирования формы.
- Успешную цель не удваивать при reload/back; маршрутный контекст очищать после подтверждённого успеха. Отсутствие аналитики/хранилища не блокирует пользователя.
- Для звонков до коллтрекинга измеряется только клик по номеру, **не состоявшийся звонок**. Коллтрекинг и CRM не включать в реализацию молча.

## 5. Приёмка общей интеграции до рекламы

- Все три рекламных URL с тестовыми метками — 200, контент правильного направления, canonical чистый, query не ломает ресурсы.
- Калькулятор/заявка: три допустимые пары; пустой/неполный/неизвестный/повторный параметр; неподдерживаемая пара; самонаправление; посторонние параметры; XSS-строки не попадают в HTML. Направления берутся из единого источника.
- Пустая форма, совпадающая/конфликтующая/частично восстановленная пара, reload/back, ручная смена города, очистка и восстановление последней заявки. Ни реквизиты, ни согласия не меняются неожиданно.
- Расчёт трёх маршрутов совпадает с исходным калькулятором; form JSON и серверный контракт сохранены. Ошибки/повторная отправка/блокировка кнопки проходят прежние тесты.
- Синтетическая проверка успеха/ошибок через mock, без настоящих писем и персональных данных. Живую отправку — только в отдельно согласованной тестовой среде.
- Мобильный путь реклама → лендинг → расчёт → заявка на 360 px; desktop 1280, обе темы, клавиатура, доступные CTA/ошибки, слайдер без переполнения, изображения с размерами и разумной загрузкой. Не заявлять конкретный performance score без замера.
- В Метрике/Директе проверить источник и реальный приём целей тестовым разрешённым способом. Если доступа нет — явно оставить проверку кабинетов открытой.
- После build: тесты, БЭМ и lint. Отдельно разрешённый выпуск, затем production GET/canonical/sitemap и регрессия старых 301/410.
