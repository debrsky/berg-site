# SEO-04: проектирование маршрутных страниц

Дата: **2026-10-16**. Текущий статус: **три прототипа/тексты/FAQ и рекламный контракт утверждены владельцем в продолжении сессии**. Отдельно разрешена реализация Владивосток → Хабаровск с общей интеграцией. Первая страница реализована локально, не опубликована; остальные две не свёрстаны. [Отчёт реализации и проверки](implementation-vvo-khb.md). Ни публикация, ни изменение кабинетов не разрешены. Ниже сохранена исходная спецификация; формулировки о будущей реализации описывают контракт, а не актуальный статус кода.

## Последнее расширение: вес и объём из калькулятора

Владелец отдельно разрешил перенос **введённых** веса и объёма из калькулятора в существующую заявку, с защитой сохранённых данных и без оценочных величин. ## Источники и редакционные ограничения

- Факты: [SEO-02](../business-data.md), `src/pug/business-data.pug`; SEO-03 уже опубликована и проверена.
- Цены, пороги, коды и адреса: **только** `src/pug/tariffs.pug`. Числа в прототипах — снимок для сверки от 2026-10-16, не вторая база. При вёрстке получать значения из объекта, а не копировать Markdown.
- Дни и сроки читать из отдельной записи `business.routes` по паре; `usualDays` и `days` не взаимозаменяемы. Гарантированные календарные сутки считаются от приёма груза, не от предполагаемого выхода машины. Не обещать любой груз за обычный срок.
- Приём по регламенту до 11:00 местного времени; после — возможна отправка при наличии места. Не выдавать обычный выход машин не ранее 15:00 за расписание и не обещать приём до 15:00.
- «Заявку на подачу машины на завтра необходимо подать сегодня до 16:00» — дедлайн заявки на машину, не сдачи груза и не автоматическое бронирование ближайшего рейса.
- Отправка/получение: терминал либо забор/доставка до склада отправителя/получателя. Не обещать бесплатную адресную услугу или неограниченную зону. Применимость конкретной подачи согласовывается, общие тарифы подачи остаются в pricing.
- Упаковка и обрешётка **только во Владивостоке**. Отсутствующий телефон `packaging` не подменять другим номером с той же подписью.
- Температурный режим — только «по согласованию», без температур, сроков подготовки и числовых доплат в рекламных блоках. Чекбокс и действующая логика калькулятора остаются как есть.
- Цены включают НДС; **числовую ставку не публиковать**. Страхование, охрану, рейтинги, «самые низкие цены», фиксированное расстояние и юридические гарантии без источника не добавлять.
- Режим работы в часах не установлен. Для выдачи — «Время выдачи груза обычно согласовывается по телефону». Не выдумывать часы, праздничные переносы, SLA обратного звонка.
- Использовать только собственные фотографии проекта с подтверждёнными правами владельца; допустим выпуск без новых фото. Не создавать псевдокарту реального маршрута и не брать чужие изображения из исследования.

См. [research.md](research.md). Список запросов — качественная гипотеза для трёх коммерческих намерений, **не семантическое ядро с измеренными частотами**. ## Общий контракт тарифного блока

Выводить только одну пару `origin → destination` по `price[origin][destination]`:

1. Понятная подпись «Междугородняя перевозка. Цены включают НДС» и дата действия из `tariffs.startdate`.
2. Три независимые группы: минимальные категории (руб. за отправку), тяжёлый груз (руб./кг), лёгкий груз (руб./м³). На 360 px — вертикальные таблицы «диапазон / ставка», не общая многонаправленная таблица.
3. У минимальных категорий должны одновременно выполняться пределы массы **и** объёма; выбирается первая подходящая категория. Нельзя подавать документный тариф как цену любого груза «от».
4. После минимальных категорий лёгкий груз — объём более 5 м³ на тонну, иначе тяжёлый. На границе диапазона — следующий диапазон согласно действующему калькулятору, алгоритм не менять.
5. При машинорейсе выводить «по договорённости», не `0`, `null`, `Infinity` и не брать ставку последней обычной строки. В текущем расчёте для соответствующей категории вес от 15 т либо объём от 75 м³ переводит на машинорейс.
6. Для обычной перевозки негабарита +30% по критериям текущего pricing; для обрешётки другой порог/коэффициент, не смешивать. Для ДВС калькулятор дополнительно применяет отдельный маршрутный минимум — в рекламный пример по обычному грузу не включать молча.
7. Рядом с примерами явно указать, что это **только межгород**, без забора/доставки по адресу, упаковки, платного хранения, погрузочно-разгрузочных работ и специальных условий. Условия и дополнительные расходы — `/pricing.html#extra-services`, `/terms.html`, `/package.html`.
8. Тарифы и существенные условия доступны в исходном HTML. Если таблицы сворачиваются через details, краткие условия/единицы не прячутся внутрь единственного закрытого элемента.

## Контракт калькулятора — пока НЕ реализован

Будущие CTA:

- `calculator.html?origin=vvo&destination=khb`;
- `calculator.html?origin=khb&destination=vvo`;
- `calculator.html?origin=vvo&destination=blg`.

В текущем `calculator.pug` чтения query нет. До реализации и проверки предзаполнения нельзя выпускать CTA с обещанием «маршрут уже выбран»: временно допустима только обычная ссылка на калькулятор с инструкцией выбрать города. Предпочтение — выпустить общую интеграцию до/вместе с лендингами.

Правила будущей интеграции:

- Читать только `origin` и `destination`, ровно по одному значению каждого; допустимы только коды из tariffs и существующая пара по текущему `hasRoute`. Самонаправление, неизвестный/одиночный/повторный параметр — игнорировать оба, оставить ручной выбор. Не подставлять «похожий» город.
- Предзаполнять только маршрут. Вес, объём, флажки, контакты и условия заявки из URL не принимать. Не вставлять строку запроса в HTML. Другие параметры не влияют на расчёт.
- Применить валидную пару при начальной загрузке, затем пересчитать через штатный обработчик. Не переопределять ручной выбор при каждом input или возвращении из истории; восстановленную пользователем форму не сбрасывать.
- Без JS ссылка открывает калькулятор, но автоматический расчёт/предзаполнение недоступны: на лендинге остаются HTML-тарифы, условия, телефон и ссылка на контакты. Не обещать работу калькулятора без JS.
- Canonical калькулятора всегда `https://bergvl.ru/calculator.html`, без query. В sitemap не добавлять параметризованные варианты.

## Контракт заявки

**Согласованное расширение:** CTA калькулятора также передаёт необязательные `weight`/`volume` в существующие поля заявки; при конфликте маршрута/грузовых параметров старые данные сохраняются. Подробные правила, валидация и проверки — в [calculator-transfer.md](calculator-transfer.md).

После согласованного дополнения для рекламы планируются CTA **`order.html?origin=<код>&destination=<код>`**, с предзаполнением только существующих select городов. Никаких новых полей, автосогласий и переноса клиентских данных из URL. Контракт проверки пары, порядок относительно восстановления формы и предлагаемая защита сохранённых городов — в [ads-integration.md](ads-integration.md). До реализации/проверки не обещать работающий перенос; обычная order.html с ручным выбором остаётся fallback. Не копировать форму на лендинг, не отправлять заявку фоновым действием и не создавать вторую валидацию.

## Перелинковка и доступность

Позднейшее решение владельца: логотип ведёт на home.html; все ссылки с лендинга на другие документы открываются с `target="_blank" rel="noopener"`. Якоря и tel-ссылки остаются нативными без новой вкладки. Для CTA новая вкладка получает только whitelisted `route_source`/`route_time` с исходным TTL 30 минут; UTM/yclid и пользовательские поля не копируются. См. [отчёт](implementation-vvo-khb.md).

- Главная: ссылки из соответствующих строк расписания, сохранив честный график и общие CTA. Прайс: ссылка рядом с названием/подзаголовком каждой из трёх пар, не ссылка со всей строки тарифа. При необходимости отдельный компактный блок «Подробнее о направлениях», без скрытых ссылок.
- Между vvo→khb и khb→vvo — блок «Нужно обратное направление?»; на vvo→blg не ссылаться как на обратную страницу. Для vvo→blg обратный лендинг не запланирован: ссылка на общий прайс с пояснением ручного выбора, не на несуществующий URL.
- Ссылки на ещё не выпущенный лендинг не добавлять. Поэтапный выпуск должен проверять существование каждой цели, затем включать соответствующие входящие/перекрёстные ссылки. Добавление в sitemap — только после появления индексируемого HTML с self-canonical.
- Один видимый H1, H2 по смыслу, видимые подписи CTA; ссылки — `<a>`, раскрытие — нативный details/summary. Фокус видим в обеих темах, никаких ссылок без href и кнопок только с JS.
- По уточнению владельца лендинг использует отдельный `src/pug/landing-layout.pug`: компактная шапка с брендом/маршрутным телефоном, без меню сайта, выбора города, общего объявления и типового подвала. Свои CSS/JS-бандлы; общие только данные, SEO, счётчик и логика темы. На desktop 1280 px — самостоятельный контейнер, первый экран с основной мыслью и двумя CTA, максимум две колонки в информационных блоках. На mobile 360 px сохраняется компактная шапка. Не обещать, что все блоки помещаются в один экран.
- На mobile 360 px: порядок блоков определён каждым прототипом; один столбец, CTA переносятся без горизонтального скролла, телефоны нажимаемы. Не добавлять sticky-панель, перекрывающую таблицы/форму. Содержание одинаково в HTML для обеих ширин, без дублированного скрытого SEO-текста.
- FAQ в прототипах — вопросы по согласованным условиям. Частотность/реальные обращения не подтверждены; владелец должен утвердить их практичность. FAQPage и обещания расширенного сниппета не включать в объём по умолчанию.

## Аналитика — спецификация, не настройка Метрики

Сохранить текущую цель `order successfully sent`. Новые цели должны быть созданы/согласованы владельцем в Метрике до приёмки аналитики. Не передавать персональные данные, названия грузов, адреса, телефоны клиента, стоимость/объявленную стоимость или содержимое полей формы.

| Предложенная цель | Когда отправлять | Разрешённые параметры |
|---|---|---|
| `route_calculator_click` | Пользователь активировал CTA калькулятора | `route_id`, `cta_position` |
| `route_order_click` | Пользователь активировал CTA заявки | `route_id`, `cta_position` |
| `route_phone_click` | Пользователь активировал tel-ссылку | `route_id`, `cta_position` (сам номер не передавать) |
| `route_order_success` | Только подтверждённый `data.result === 'success'` в существующем callback отправки | `route_id`, `source_page` |

- `route_id`: только `vvo-khb`, `khb-vvo`, `vvo-blg`; позиция CTA — `hero`, `tariff`, `terminal`, `bottom`. `source_page` — только один из трёх фиксированных slug, не произвольный URL/referrer.
- Для перехода на order.html можно хранить отдельную от предзаполнения атрибуцию в sessionStorage при клике: пара, slug и время клика, TTL 30 минут, last-click в текущей вкладке. Это **не предзаполнение формы**. Запрет хранилища/аналитики не блокирует переход/отправку; атрибуция в этом случае отсутствует.
- Если посетитель вручную поменял города в заявке, `route_id` обозначает источник перехода, **не доказанный фактический маршрут заявки**. Не выводить конверсию по фактическим перевозкам из этих событий.
- `route_order_success` отправлять один раз в успешном callback до перехода на order-ok, затем очищать контекст. Не создавать конверсию по загрузке order-ok, клику Submit, HTTP 200 без success или при ошибке; сбой ym не должен ломать существующее подтверждение/редирект.
- Открытые цели аналитики и её блокировщики учитывать как ограничение полноты. Реальные письма ради проверки не отправлять без отдельной согласованной среды.

### Измерение результата

До публикации: сохранить доступный базовый срез Вебмастера/Метрики по каждой маршрутной группе, бренду и документам за сопоставимый период; новых URL в базе ещё нет. Если отчётов нет, явно записать отсутствие, не подставлять общий CTR сайта как маршрутный. После выпуска сравнить 4/8/12 недель: индексация URL, показы/клики коммерческих маршрутных запросов, переходы в калькулятор/заявку, подтверждённые успешные отправки с оговоркой атрибуции. Учитывать сезонность и задержки; позиции/рост не являются гарантированным критерием реализации.

## Предлагаемый план последующей реализации

После утверждения владельцем оформить отдельные задачи:

1. Общая интеграция: контракт query калькулятора с тестами; генератор тарифной выборки и примеров из tariffs; аналитика с безопасным контекстом и сохранением текущей цели. Добавить предзаполнение городов в существующей заявке по рекламному дополнению; не менять алгоритм цены, состав полей или PHP/JSON-контракт.
2. Вёрстка vvo→khb по его прототипу; тесты метаданных/сроков/данных; локальный просмотр.
3. Вёрстка khb→vvo; отдельные проверки обратного тарифа и отсутствия обещания упаковки в Хабаровске.
